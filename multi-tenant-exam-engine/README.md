> **实战目标**：深入解构大型在线教育与企业在线考试系统（如高星开源项目 `sg-exam`）的**行级多租户隔离内核与动态配额智能组卷算法**。基于 `TenantContext` 租户上下文透传、底层 SQL AST 行级条件拦截注入、切屏防作弊状态机与客观题秒级批改，实现 100% 数据防泄露与高可用评测闭环。

## 🚀 场景痛点分析

在 SaaS 化在线教育、高校多院系统考或集团企业内训场景中：
1. **多租户数据泄露红线**：若由业务人员在每个 SQL 中手工书写 `WHERE tenant_id = ?`，只要漏写一个条件，就会导致 A 机构的学生看到 B 机构的绝密考试题库，引发严重法务纠纷；
2. **并发动态组卷性能瓶颈**：全真严肃考试需要“千人千卷”（同一场考试每个学生的题序不同、抽题不同），若缺乏精准的难度与题型配额采样算法，组卷耗时过长，瞬间打垮数据库；
3. **线上考试防作弊难度大**：浏览器切屏查答案、超时提交等行为必须具备轻量级、确定性的规则拦截引擎。

## ⚠️ 小白排坑要点 (Common Pitfalls)

1. **缓存穿透导致的多租户串门（Cache Tenant Leak）**：
   - 在多租户系统中，如果使用 Redis 缓存试卷或题目数据，**缓存 Key 必须前置携带 tenant_id**（如 `exam:paper:{tenant_id}:{exam_id}`）。若直接以 `exam:paper:{exam_id}` 作为 Key，租户 1 查询缓存后，租户 2 的请求命中同一缓存，直接导致跨租户越权。

2. **异步线程池与 ThreadLocal 上下文丢失**：
   - 在 Spring Boot 中如果使用 `@Async` 异步处理阅卷或判分任务，`ThreadLocal` 中的 `tenant_id` 不会自动传递给子线程，导致子线程执行查询时因缺少租户上下文而报错或查出空数据。
   - **防御手段**：配置 `TaskDecorator` 包装线程，在任务提交时克隆当前线程的租户上下文，执行完成后清理。

3. **动态组卷的随机种子偏斜**：
   - 高并发下大量学生同时点击“开始答题”时，若直接在 SQL 中使用 `ORDER BY RAND() LIMIT N`，会导致全表全量扫描与临时文件排序，瞬间压垮数据库。
   - **排错解法**：先通过主键索引批量获取当前租户题目 ID 列表，在应用层通过加权随机算法采样 ID，再利用 `WHERE id IN (...)` 回表查询，性能提升数十倍。
