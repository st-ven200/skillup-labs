## 1. 实验场景与核心目标

在单体系统拆分为分布式微服务集群后，系统的复杂度急剧上升。下游微服务的网络延迟、暂时性故障或过载极易通过调用链逆向蔓延，引发线程池耗尽与全链路雪崩。

本实验通过自包含的弹性服务聚合引擎，深入验证以下核心能力：
1. **聚合器模式 (Aggregator Pattern)**：利用多线程池并发扇出调用下游用户服务、订单服务、推荐服务与积分服务，统一聚合大卡片数据并降低端到端延迟。
2. **自适应断路器状态机 (Circuit Breaker)**：实现标准的 `CLOSED` $\rightarrow$ `OPEN` $\rightarrow$ `HALF_OPEN` $\rightarrow$ `CLOSED` 三态转移逻辑。
3. **极速短路与优雅降级 (Fallback)**：下游故障时在 0.5ms 内快速短路阻断，返回兜底默认数据，防止网关线程池阻塞。
4. **金丝雀探测与自动愈合**：在熔断冷却期结束后自动放行探测流量，当下游服务恢复健康时自动解除熔断。

## 3. 生产踩坑排障实录 (Pitfalls)

1. **聚合器模式下的线程池隔离隔离防线**：
   - 如果所有下游微服务的并发调用共享同一个线程池，当某个冷门依赖（如风控审查或推荐）发生毫秒级阻塞时，整个线程池的所有 Worker 会在瞬间被占满，导致原本健康的核心链路（如用户鉴权、订单支付）无法申请到可用线程而全面瘫痪。**生产环境中必须为不同重要级的下游依赖配置独立隔离的线程池或信号量（Bulkhead Pattern 舱壁隔离）**。
2. **断路器半开状态（HALF_OPEN）的瞬时并发击穿**：
   - 当断路器从 `OPEN` 冷却结束转入 `HALF_OPEN` 时，如果并发量极高，必须严格限制只能有 1~2 个金丝雀（Canary）请求真正穿透到底层微服务，其余并发请求依然直接执行本地 Fallback 降级，避免刚刚苏醒的下游服务再次被海量并发瞬间冲垮。
3. **降级数据的脏数据缓存污染**：
   - 在执行 Fallback 兜底逻辑时，如果本地使用了分布式缓存（如 Redis），必须明确区分“业务有效缓存”与“降级假数据缓存”。严禁将降级生成的默认兜底数据写入具备较长 TTL 的共享缓存中，否则即使下游服务完全恢复，前端用户在数小时内依然会看到兜底的假数据。
